# Deployment Guide — AccessSlot

Deploying to production on Render using Docker (backend) and Static Site (frontend).

---

## 1. Architecture

```
GitHub Repository (Hima6-bindu/accessslot)
         │
         ├── backend/          → Render Docker Web Service
         │   └── Dockerfile        python:3.11-slim + gunicorn
         │
         ├── frontend/         → Render Static Site
         │   └── (vite build)      served via Render CDN
         │
         └── render.yaml       → Render Blueprint (creates all services)

Render Services:
  accessslot-backend    Docker Web Service    https://accessslot-backend.onrender.com
  accessslot-frontend   Static Site           https://accessslot-frontend.onrender.com
  accessslot-db         PostgreSQL (managed)  (internal connection only)
```

### Why this architecture

- **Backend as Docker:** Full control over Python version, system packages (libpq), and startup sequence (migrations run automatically on container start).
- **Frontend as Static Site:** The Vite build produces pure static files. Render serves these from a global CDN — faster, cheaper (free tier), and no cold-start delays compared to a Docker container.
- **Database as managed service:** Render handles backups, updates, and connection pooling.

## 2. Pre-Deployment Checklist

Before pushing to GitHub and deploying, confirm:

- [ ] `backend/Dockerfile` exists
- [ ] `backend/.dockerignore` exists
- [ ] `frontend/Dockerfile` exists (used for local testing only)
- [ ] `frontend/nginx.conf` exists
- [ ] `render.yaml` is committed to the repo root
- [ ] `backend/.env` is **NOT** committed (check: `git status | grep .env`)
- [ ] All new files are committed and pushed to `main`

### Commit the Docker files

```powershell
cd d:\accessslots\accessslot

git add backend/Dockerfile
git add backend/.dockerignore
git add backend/.env.example
git add backend/.gitignore
git add frontend/Dockerfile
git add frontend/.dockerignore
git add frontend/.env.example
git add frontend/nginx.conf
git add docker-compose.yml
git add render.yaml

git commit -m "Add Docker configuration for production deployment"
git push origin main
```

## 4. Deploy Using Blueprint (Recommended)

Render's Blueprint feature reads `render.yaml` and creates all services automatically.

### Step 1 — Create Blueprint

1. In the Render dashboard click **"New +"** → **"Blueprint"**
2. Select the `Hima6-bindu/accessslot` repository
3. Select branch: `main`
4. Render will detect `render.yaml` and show you a preview of the 3 services it will create:
   - `accessslot-db` (PostgreSQL)
   - `accessslot-backend` (Docker Web Service)
   - `accessslot-frontend` (Static Site)
5. Review the list — do not click Apply yet

### Step 2 — Set Manual Environment Variables

Before clicking Apply, set the two `sync: false` variables:

**On `accessslot-frontend`:**
- `VITE_API_BASE_URL` = `https://accessslot-backend.onrender.com/api`

**On `accessslot-backend`:**
- `CORS_ALLOWED_ORIGINS` = `https://accessslot-frontend.onrender.com`

> If you are not sure of the exact URLs yet, set placeholder values and update them after the first deploy. See section 7 (CORS fix) below.

### Step 3 — Apply Blueprint

Click **"Apply"**. Render will:
1. Create the PostgreSQL database
2. Deploy the backend (Docker build — takes 3–5 minutes)
3. Deploy the frontend (npm build — takes 1–2 minutes)

Watch the deploy logs for any errors.

## 5. Environment Variables Reference

### Backend (Docker Web Service)

| Variable | Value | Source |
|---|---|---|
| `SECRET_KEY` | *(auto-generated by Render)* | Render "Generate" |
| `DEBUG` | `False` | Manual |
| `ALLOWED_HOSTS` | `accessslot-backend.onrender.com,localhost,127.0.0.1` | Manual |
| `DB_NAME` | *(from database)* | Linked from `accessslot-db` |
| `DB_USER` | *(from database)* | Linked from `accessslot-db` |
| `DB_PASSWORD` | *(from database)* | Linked from `accessslot-db` |
| `DB_HOST` | *(from database)* | Linked from `accessslot-db` |
| `DB_PORT` | *(from database)* | Linked from `accessslot-db` |
| `JWT_ACCESS_TOKEN_LIFETIME` | `60` | Manual |
| `JWT_REFRESH_TOKEN_LIFETIME` | `1440` | Manual |
| `SECURE_SSL_REDIRECT` | `False` | Manual — **must be False** |
| `CORS_ALLOWED_ORIGINS` | `https://accessslot-frontend.onrender.com` | Manual |

### Frontend (Static Site)

| Variable | Value | Notes |
|---|---|---|
| `VITE_API_BASE_URL` | `https://accessslot-backend.onrender.com/api` | Build-time — baked into JS bundle |
| `NODE_VERSION` | `22` | Tells Render which Node to use |

> **Important:** `VITE_API_BASE_URL` is a **build-time** variable. Changing it in the Render dashboard triggers a rebuild. You cannot change the API URL at runtime without rebuilding.

## 6. Docker Configuration

### Backend Dockerfile summary

```
FROM python:3.11-slim
  → installs libpq-dev, gcc (for psycopg2)
  → creates non-root user (appuser)
  → pip install -r requirements.txt
  → python manage.py collectstatic (build time)
  → CMD: python manage.py migrate && gunicorn ... --bind 0.0.0.0:$PORT
```

Key points:
- Binds to `0.0.0.0:$PORT` — Render injects `PORT` automatically
- Migrations run automatically on every container start
- Static files are collected at image build time (not at runtime)
- Runs as non-root user (`appuser`) for security

### Frontend Dockerfile summary (local testing only)

```
Stage 1 (node:22-alpine):  npm ci → vite build → /app/dist
Stage 2 (nginx:alpine):    copy dist → /usr/share/nginx/html
                           custom nginx.conf with SPA routing
```

On Render, the frontend is deployed as a Static Site — this Dockerfile is only used for `docker compose` local testing.

## 7. Deployment Steps (First Time)

### Step 1 — Verify the backend deployed

Check the deploy logs in the Render dashboard. You should see:
```
Applying migrations...
  Applying users.0001_initial... OK
  Applying equipment.0001_initial... OK
  ...
[INFO] Starting gunicorn 23.0.0
[INFO] Booting worker with pid: ...
```

Then test the health check:
```
https://accessslot-backend.onrender.com/api/health/
```

Expected response:
```json
{"status": "ok", "service": "AccessSlot API", "database": "connected"}
```

### Step 2 — Verify the frontend deployed

Navigate to:
```
https://accessslot-frontend.onrender.com
```

The React app should load. Open browser DevTools → Network tab and check that API calls go to `https://accessslot-backend.onrender.com/api`.

### Step 3 — Fix CORS if needed

If the frontend cannot reach the backend (CORS error in browser console):

1. In the Render dashboard, go to `accessslot-backend` → **Environment**
2. Set `CORS_ALLOWED_ORIGINS` = `https://accessslot-frontend.onrender.com`
3. Click **Save** — Render triggers an automatic redeploy
4. Wait for the redeploy to complete
5. Refresh the frontend

### Step 4 — Create an admin user

```
# In the Render dashboard: accessslot-backend → Shell (or use logs)
# Or trigger a one-off job:

python manage.py createsuperuser
```

## 8. Health Checks

### Backend health check

- **Path:** `/api/health/`
- **Method:** GET
- **Auth required:** No (public endpoint)
- **Success response:**
  ```json
  {"status": "ok", "service": "AccessSlot API", "database": "connected"}
  ```
- **Failure response (DB down):**
  ```json
  {"status": "ok", "service": "AccessSlot API", "database": "error", "database_error": "..."}
  ```
  HTTP 503

Render checks this endpoint every 30 seconds. If it returns non-200 three times in a row, Render marks the service unhealthy and attempts a restart.

### Frontend health check

Static sites do not have a configurable health check on Render. The CDN simply serves files.

## 9. Logs

### View logs in Render dashboard

1. Go to your service (`accessslot-backend`)
2. Click **"Logs"** in the left sidebar
3. Logs are live-tailed by default

### What to look for in backend logs

Normal startup:
```
Running migrations...
Applying equipment.0004_maintenance_and_waitinglist... OK
[INFO] Starting gunicorn 23.0.0
[INFO] Booting worker with pid: 9
[INFO] Booting worker with pid: 10
```

Normal request:
```
10.x.x.x - - [02/Oct/2026:18:40:51 +0000] "GET /api/health/ HTTP/1.1" 200 65
```

Error patterns to watch for:
- `OperationalError: could not connect to server` → database not reachable
- `ImproperlyConfigured` → missing environment variable
- `DisallowedHost` → `ALLOWED_HOSTS` does not include the request hostname

## 10. Troubleshooting

### Backend: `DisallowedHost` error

**Symptom:** 400 Bad Request, logs show `Invalid HTTP_HOST header`

**Fix:** Add the Render hostname to `ALLOWED_HOSTS`:
```
accessslot-backend.onrender.com,localhost,127.0.0.1
```
Update in Render dashboard → Environment → redeploy.

---

### Backend: `UndefinedValueError` for SECRET_KEY

**Symptom:** Container fails to start, logs show `UndefinedValueError: SECRET_KEY not found`

**Fix:** The `SECRET_KEY` environment variable is missing. In Render dashboard → Environment → add `SECRET_KEY` with a generated value.

---

### Backend: Database connection error

**Symptom:** `django.db.utils.OperationalError: could not connect to server`

**Fix:** Check that all `DB_*` variables are correctly linked to the `accessslot-db` database service. In Render, use "Link" to connect them from the database rather than manually typing values.

---

### Frontend: Blank page / CORS error

**Symptom:** React app loads but all API calls fail with CORS error

**Fix:**
1. Check `CORS_ALLOWED_ORIGINS` on the backend includes the exact frontend URL (including `https://`)
2. Check `VITE_API_BASE_URL` on the frontend matches the exact backend URL
3. Rebuild the frontend (change any env var and revert to trigger a rebuild)

---

### Backend: `SECURE_SSL_REDIRECT` redirect loop

**Symptom:** ERR_TOO_MANY_REDIRECTS

**Cause:** `SECURE_SSL_REDIRECT=True` causes Django to redirect to HTTPS, but Render's proxy already handles HTTPS — Django sees plain HTTP internally and redirects infinitely.

**Fix:** Set `SECURE_SSL_REDIRECT=False`. Render handles TLS termination at the proxy layer. Django's `SECURE_PROXY_SSL_HEADER = ('HTTP_X_FORWARDED_PROTO', 'https')` is already configured to trust Render's forwarded header.

---

### Slow cold starts on free tier

**Symptom:** First request after 15 minutes of inactivity takes 30–60 seconds

**Cause:** Render's free tier spins down containers after 15 minutes of inactivity.

**Options:**
- Accept it (fine for development/staging)
- Upgrade to a paid plan (containers stay warm)
- Set up an external uptime monitor to ping `/api/health/` every 10 minutes

## 11. Redeployment Procedure

### Automatic redeploy (default)

Every push to the `main` branch triggers automatic redeployment of both services.

### Manual redeploy

In the Render dashboard:
1. Go to the service
2. Click **"Manual Deploy"** → **"Deploy latest commit"**

### Rollback

1. Go to the service → **"Deploys"** tab
2. Find the previous successful deploy
3. Click **"Rollback to this deploy"**

### Environment variable change

Changing any environment variable in the Render dashboard automatically triggers a redeploy of that service.

## 12. Custom Domain (Optional)

To use a custom domain instead of `.onrender.com`:

### Backend
1. `accessslot-backend` → **Settings** → **Custom Domains**
2. Add your domain (e.g. `api.yourdomain.com`)
3. Update `ALLOWED_HOSTS` to include it
4. Update `CORS_ALLOWED_ORIGINS` on the backend to include the frontend custom domain

### Frontend
1. `accessslot-frontend` → **Settings** → **Custom Domains**
2. Add your domain (e.g. `yourdomain.com`)
3. Update `CORS_ALLOWED_ORIGINS` on the backend
4. Rebuild the frontend with `VITE_API_BASE_URL` pointing to the backend custom domain

## 13. Free Tier Limitations

| Limitation | Detail |
|---|---|
| PostgreSQL | 1 GB storage, 90 days before expiry (must re-create) |
| Web Service | Spins down after 15 min inactivity, 750 hrs/month |
| Static Site | Unlimited bandwidth, always on |
| Build minutes | 500 per month |

For a production app with real users, upgrade the database and backend to a paid plan.
